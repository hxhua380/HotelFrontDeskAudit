# Stage 3 核对规则

本阶段实现离线、确定性的 TypeScript 核对。生产路径只使用订单、可用录音及原始转写，不访问人工答案、模型或网络。`Order`、`Recording`、`Evidence`、`AuditResult` 的原接口保持不变，新增信息通过派生类型表达。

## 输入与调用

```ts
queryOrdersByDate(date, ordersFile?): Promise<Order[]>
queryRecordingsByDate(date, recordingsFile?, audioRoot?): Promise<RecordingQueryResult>
extractTranscript(recording): TranscriptFacts
auditDay(orders, recordings, date, options?): DetailedAuditResult[]
```

`date` 必须是有效的 `YYYY-MM-DD`。订单按 `handled_at`、录音按 `started_at` 的北京时间日期筛选，住宿日期不参与这个筛选。时间戳须满足原契约的 `+08:00` 格式。查询每次重新读取 JSON，不缓存旧文件。默认文件地址相对于模块解析，命令可从其他工作目录启动。

录音查询返回 `{ recordings, warnings }`，其中只包含当天文件存在且为普通文件的录音。`audio_missing` 或 `audio_not_file` 警告包含录音编号、开始时间、路径和说明。JSON、字段、日历日期、重复编号或路径非法时直接报错。路径必须相对根目录；检查规范化路径和实际路径，包括不存在叶子文件的最近存在父目录，拒绝通过链接越界。音频解码和声学质量由 Stage 2 的 `validate:data` 检查负责，查询本身不重新解码。

CLI 执行两种查询，再把可用录音及警告交给纯函数 `auditDay`。警告始终输出在 CLI 顶层；与订单在候选窗口内的警告也附加到该订单的结果。缺失文件的元数据不产生虚假的录音候选或片段证据。

## 可观察信息提取

每个字段返回 `{ value, ambiguous, observations }`。未知为 `value: null, ambiguous: false, observations: []`；观察到多个不同值时为 `value: null, ambiguous: true`，并保留全部原始观察。重复观察到同一值不构成歧义。未知既不算一致，也不算冲突。

每条观察包含值和 `TranscriptEvidence`：`recording_id`、从零开始的 `segment_index`、完整原始 `text`、`start_ms`、`end_ms`、字段归属。只引用已有片段范围，不根据文本位置虚构词级时间戳。

| 字段 | 支持的表达 | 保守边界 |
| --- | --- | --- |
| 房号 | `房号802`、`802号`、`八零二号`、`八〇二房间`，保留前导零 | 无房号上下文的裸数字不猜；过滤日期、金额及单位串 |
| 房型 | 明确列举的大床房、双床房、豪华大床房、套房等常见名称，优先最长名称 | 不推断缩写、未列出的同义词或房型等级 |
| 日期 | `2026年10月15日`、`二零二六年十月十五日`、`10月15日`、`十月十五号`、带标签的 ISO 日期 | 必须有关联的入住/退房标签或明确住宿区间 |
| 相对日期 | `今天入住`、`明天退房`、`后天退房` | 基于录音开始时刻的北京时间，独立于运行当天 |
| 金额 | `398元`、`三百九十八元`、`一共三百九十八块`、`人民币398元`、`398.50元` | 使用整数/BigInt 转换到安全整数分，不做浮点元金额运算 |

省略年份的月日使用录音年份；同一原始片段内明确月份可为后续的“十六日退房”提供月份。不会自动推断跨年住宿或跨月回绕。无效日历日期保留未知。

`可能`、`大约`、`左右`、`或更多` 等不确定表达、金额/房号范围、每晚单价和缺乏可靠解释的中文缩略金额不当作确定值。押金、定金、订金、退款不作为订单房费；同段有多种费用时仅采纳明确房费/房款/住宿费。`398或428元`、`明天或后天退房` 等明确替代项保留歧义。解析器不处理所有中文否定、更正、指代和谈话关系；不使用 LLM 计算或补全。

## 候选图与业务区分

1. 先校验日期和输入时间戳，再选当天记录。
2. `abs(handled_at - started_at) <= window_seconds` 建边，默认 `window_seconds: 180`，边界包含 180 秒。配置须为大于等于零的有限数。
3. 提取五项字段。时间接近仅表示候选，不确认身份。
4. 有明确且无歧义房号时，允许用业务内容缩小边：没有同房号订单则保留原候选，以允许房号冲突；存在同房号订单时，若其中有五字段全一致候选，则只保留同房号候选。否则保留同房号候选及其他房号但两日期、房型、金额四项全一致的候选。不会让弱房号证据掩盖强四字段冲突候选。
5. 对剩余二部图取连通分组。每个订单和录音只属于一个分组；任一侧数量大于一时整个组为 `needs_review`。不按最近时间、编号大小或数组顺序选胜者。

排序仅保证输出稳定，不决定业务对应。多候选组保留所有 `candidate_order_ids` 和 `candidate_recording_ids`，不能再把参与者重复标为缺录音或孤立录音。同一录音不能确认给多个订单。

## 单候选的身份确认与字段比较

正向身份依据满足下面任一规则：

- 房号一致，且入住日期、退房日期、房型中至少一项明确一致；
- 入住日期、退房日期、房型、金额四项均明确一致，允许进一步报告房号冲突。

只有身份可靠才可输出 `matched` 或 `field_mismatch`。比较范围为房号、房型、入住日、退房日、金额。金额不同不会删除已有的房号和日期身份依据。仅金额相同或仅时间相近不能确认身份。全部已知关键字段都相反时保留复核，不强行匹配。

| 状态 | 条件 |
| --- | --- |
| `matched` | 一对一、身份可靠、五字段全已知且无歧义、全部一致 |
| `field_mismatch` | 一对一、身份可靠、没有提取歧义，且有明确字段冲突；其他未知字段仍在理由中列出 |
| `missing_recording` | 订单节点没有合理的可用录音边；证据为空 |
| `orphan_recording` | 可用录音节点没有订单边；引用真实原句证据 |
| `needs_review` | 多候选、提取有歧义、缺乏身份证据或核实信息不足 |

`conflicts` 为每项已知差异提供 `field`、`order_value`、`recording_value` 和原始证据。单候选复核也可以列出观察差异，但它不等于已确认事件冲突，必须结合 `status` 和 `reasons` 解读。多候选组不虚构具体配对的冲突。

`order_id` / `recording_id` 在该侧只有一个候选时保留，多个候选时为 `null`。在 `needs_review` 中这两个标量只是唯一候选的引用，不能解释为确认配对。该约定兼容冻结的 C005 人工答案：O004/R004 只表示一个候选组，理由明确说明未确认；其余候选集合完整保留。

## 验证与限制

通用单元测试使用独立编号和业务内容。真实数据评价器仅位于测试中，按候选集合独立定位结果并比较状态、标量候选引用与冲突字段。动态测试改动内存/临时副本中的金额、元数据、文件可用性、日期、编号、时间及关键台词，不修改正式数据。正式数据及音频在测试前后核对哈希。

规则面向当前常见中文前台话术。暂不解析中文小数/角分、千分位、复杂更正/否定、跨句指代或全部房型同义词；不合并跨录音的零散字段，不解决复杂多对多的最佳分配，不跨办理日期搜索。大规模数据的候选构建当前为 O(订单数 × 录音数)。文件检查与后续播放之间仍有文件系统竞态，现有 Web 音频路由继续处理实际读取时的不可用文件。
